# مفاتيح الذكاء الاصطناعي في نون: مراجعة قبل التنفيذ

## الخلاصة

لا يمكن إضافة مفتاح بأمان من لوحة مدير في الأساس الحالي: لا توجد مصادقة مدير خادمية، ولا صلاحيات خادمية، ولا Secret Manager، ولا سجل إعدادات موثوق. لذلك **لم نضف لوحة أو حقل مفتاح**. أضفنا فقط رفضًا صريحًا للمسارات المحجوزة `/api/admin/ai` وفروعها قبل تحليل محتوى الطلب، مع بقاء الذكاء الاصطناعي معطلًا بالكامل. هذا ليس نظام مصادقة ولا إدارة أسرار مكتملة.

النطاق المقصود هو `noon.roubex.com`. Gemini غير مسموح به لمستخدمي نون القاصرين في الإنتاج، ومفتاحه الموجود يخص المختبر الخاص وحده. لا OpenAI ولا أي مزوّد آخر معتمد في هذه المراجعة. قائمة المزوّدين المؤهلين **فارغة**، ولا يكفي امتلاك مفتاح أو موافقة مدير لتغيير ذلك.

## التغيير المنفذ في فرع المراجعة فقط

- [`server/security/admin-ai-boundary.ts`](../../server/security/admin-ai-boundary.ts): رفض كل الطرق تحت `/api/admin/ai` مع 503، `Cache-Control: no-store`، ورسالة عامة لا تعيد محتوى الطلب. لا قراءة لمفتاح، لا اتصال مزوّد، لا تخزين، ولا سجل يحتويه.
- تركيب الرفض قبل `express.json` وقبل static/SPA؛ فلا يتحول مسار إعدادات مجهول إلى صفحة نجاح ظاهرية، ولا يصل محتوى المفتاح إلى محلل JSON في التطبيق. سيستقبل خادم HTTP البايتات على مستوى النقل؛ هذا ليس ضمانًا ضد logging في وكيل خارجي.
- [`tests/admin-ai-boundary.test.ts`](../../tests/admin-ai-boundary.test.ts): طرق HTTP متعددة، محاولات انتحال دور المدير، أسماء مزوّدين، JSON تالف وكبير، عدم التسريب وعدم الوصول للمعالجات التالية.
- لا مسار تفعيل جديد، لا حقل شكلي، لا استيراد سر، لا تعديل للمختبر الخاص، ولا نشر أو دمج.

## كيف تصبح اللوحة حقيقية لاحقًا

### 1. هوية مدير يثبتها الخادم

اختيار نظام هوية قرار منفصل. المطلوب حسابات مدير محددة، MFA وإعادة تحقق حديثة لتغييرات المفاتيح، ودعوة/إلغاء وصول من جهة موثوقة. يتحقق الخادم من الجلسة وصلاحياتها في **كل طلب**؛ لا يقبل `role` أو `isAdmin` من body أو localStorage أو header يرسله العميل. جلسة قصيرة قابلة للإبطال، cookie من نوع HttpOnly وSecure وSameSite مناسب، CSRF token وفحص Origin للعمليات المعدلة، ومعدل طلبات محدود.

تقسيم الصلاحيات المقترح: `ai.config.read` لعرض بيانات غير حساسة، `ai.credentials.write` للإضافة/التدوير، `ai.config.disable` للتعطيل، و`ai.config.activate` للتفعيل بعد الموافقات. لا تمنح هذه الأدوار حق اعتماد أهلية المزوّد أو تعديل قائمة السماح. الاختبارات تشمل مديرًا ألغيت صلاحياته، مستخدمًا عاديًا، جلسة منتهية وCSRF ومحاولة الوصول لمورد بيئة أخرى.

### 2. حفظ السر خارج قاعدة البيانات العامة

يلزم اختيار Secret Manager فعلي أو مخزن أسرار خادمي مخصص بعزل وتشفير ونسخ احتياطي وسياسة وصول مكافئة، ثم اختباره؛ لا ندعي توفره الآن. هوية تشغيل الخادم فقط لها حق قراءة إصدار السر المحدد؛ متصفح المدير لا يحصل على بيانات اعتماد المخزن، ولا على قيمة مفتاح سبق حفظه. مفاتيح التشفير منفصلة عن البيانات. واجهة تغيير الإعدادات لا تملك قائمة كل أسرار المؤسسة.

التدفق المستقبلي: يدخل المدير المفتاح مرة واحدة عبر HTTPS؛ يمر مؤقتًا من حقل الإدخال إلى endpoint خادمي محمي، ثم إلى Secret Manager. **لا حفظ في الواجهة**: لا local/sessionStorage، لا IndexedDB، لا service-worker cache، لا analytics/session replay أو console؛ يُمسح الإدخال بعد الإرسال. لا يمر في URL أو GET أو VITE_* أو حزمة JavaScript أو build log. البيانات العامة تخزن فقط معرّف المزوّد، مرجع إصدار سر مبهم، الحالة، رقم مراجعة الإعدادات والموافقات؛ لا المفتاح ولا نسخة مشفرة منه في DB عادية ولا جزءًا منه لإظهار «آخر أحرف».

استدعاء المزوّد من الخادم فقط؛ endpoint محدد في سجل موثوق، لا URL يكتبه المدير، لمنع SSRF/تسريب المفتاح. لا اختبار تلقائي بمحتوى طالب ولا نقل مستنداته عند حفظ المفتاح. رفض الحقول غير المعروفة وحدود طول وحجم صارمة، بلا تسجيل الجسم أو هيدر Authorization. يجب مراجعة proxy وAPM وتقارير الأخطاء أيضًا، لا كود التطبيق وحده.

### 3. قبول مزوّد مؤهل فقط

تعرض اللوحة مستقبلًا خيارات السجل الخادمي المعتمد فقط، بلا حقل اسم/عنوان حر وبلا خيار Gemini في إنتاج نون. الخادم يعيد التحقق من الأهلية عند الحفظ **وعند كل استدعاء**؛ تغيير اسم الواجهة أو رفع علم تشغيل لا يكفي. لا قائمة مزوّدين معتمدة في هذا الفرع، ولا تكامل يعمل.

قبل إدخال مزوّد في السجل: مراجعة نصوص الشروط الرسمية الحالية للخدمة/الخطة/API والمنطقة المستهدفة، والفئات العمرية بما فيها دون 13 إن كانت ضمن الجمهور، والحسابات المدرسية وموافقات الوالدين حيث تلزم. توثيق قرار مراجعة مسؤول مع روابط النصوص ونسخها/إصداراتها وتاريخ مراجعة وانتهاء وصاحب الموافقة، إضافة إلى الاحتفاظ والتدريب على البيانات والحذف وموقع المعالجة وDPA ومتطلبات الأمان المناسبة للطلاب. لا نستنتج الأهلية من التسويق أو قبول التسجيل وحده؛ لم نراجع أو نُؤهل أي مزوّد في هذه المهمة.

حالات السجل المقترحة: غير مراجع ← تحت المراجعة ← معتمد بحدود وجمهور ومدة محددة ← منتهي/موقوف. أي غياب أو انتهاء للموافقة يعطل الطلبات. منع Gemini في الإنتاج سياسة مستقلة صريحة لا يستطيع مدير الإعدادات إزالتها. المختبر منفصل بهوية وأسرار وشبكة وبيانات اختبار لا بمتغير واجهة أو query parameter؛ لا يقرأ إنتاج نون سر المختبر ولا يعمل كممر إليه.

### 4. الإضافة والتدوير والتعطيل

وجود مفتاح لا يعني تفعيل الخدمة. حالات الإعداد المقترحة: `unconfigured` → `disabled` بمفتاح محفوظ → `pending-approval` → `active` فقط بعد قرار منفصل؛ و`revoked`/`error` تعيدان رفض الطلبات. إضافة السر وتدويره لا تفعلان المزوّد تلقائيًا.

- **إضافة:** بعد تحقق الهوية والصلاحية وCSRF والأهلية، ينشئ الخادم إصدارًا في Secret Manager ويحتفظ بالمرجع فقط؛ عند فشل أي مرحلة لا ينشر مرجعًا نشطًا. لا يُجرى اتصال جديد بالمزوّد دون قرار يسمح بذلك.
- **تدوير:** MFA حديث، طلب idempotent ورقم مراجعة لمنع تعارض مديرين، إصدار جديد غير نشط، تحقق مسموح ومعزول، تبديل مرجع ذري عند النجاح. يبطل cache وأي نسخ ذاكرة الخادم. يُلغى المفتاح القديم لدى المزوّد بإجراء معتمد مستقل؛ حذف الإصدار محليًا لا يلغي المفتاح عند مصدره. الرجوع لا يعيد مفتاحًا ملغى أو مزوّدًا فقد أهليته.
- **تعطيل:** يغلق بوابة الطلبات أولًا ويزيد جيل الإعدادات ويمنع retry/fallback؛ يلغي الجاري قدر الإمكان، مع التنبيه أن طلبًا أُرسل بالفعل للمزوّد لا يمكن ضمان سحبه. يعطل كل نسخ الخادم ويؤكد ذلك؛ فشل المخزن/التزامن يعني رفض الطلبات، لا إبقاء مفتاح cached نشطًا. يمكن الاحتفاظ بمرجع معطل وفق سياسة المدة، لا إعادة تفعيله تلقائيًا. إلغاء المفتاح لدى المزوّد خطوة منفصلة موثقة.
- **الحذف:** سياسة احتفاظ وحذف مخزن الأسرار ونسخه الاحتياطية بمراجعة؛ لا حذف غير قابل للعكس كجزء ضمني من زر التعطيل.

### 5. سجل إعدادات بلا مفتاح

يسجل السجل الخادمي المحمي من العبث: معرّف الحدث والوقت، معرّف المدير الداخلي، نوع العملية، المزوّد/البيئة، الحالة السابقة واللاحقة ورقم المراجعة ومعرّف الموافقة/الطلب والنتيجة ورمز فشل ثابت. لا body ولا مفتاح ولا جزء منه ولا Authorization أو cookies أو نص مستند طالب، ولا رسائل SDK الخام. عرض السجل بصلاحية قراءة مستقلة، مع منع المدير العادي من تعديله وحذفه وسياسة احتفاظ وتصدير معتمدة.

يلزم مسار موثوق لتسجيل intent/outcome وإعادة التوفيق عند فشل Secret Manager أو DB أو السجل؛ لا يُفعّل أو يُدوّر مع فقد التدقيق. التعطيل الطارئ لا ينتظر سجلًا متعطلًا: يُطبق رفض آمن ويكتب في journal آمن/إنذار ثم يعاد توفيق الحدث؛ هذه البنية غير موجودة بعد. تعطل التبعيات يعني AI معطلًا افتراضيًا، وليس استخدام سر قديم صامتًا.

## عقد API المقترح — غير منفذ وغير متاح

المسارات التالية تصميم فقط تحت `/api/admin/ai`؛ **كلها ترجع 503 حاليًا**، ولا يعني وصفها وجود المصادقة المطلوبة:

| المسار المستقبلي | السلوك بعد استيفاء البوابات |
| --- | --- |
| `GET /providers` | بيانات السجل المؤهلة وحالات الإعداد دون أسرار؛ غير المصرح له يُرفض. |
| `POST /providers/:id/credentials` | حفظ أول إصدار معطّل بصلاحية كتابة وMFA، لا يعيد قيمة السر. |
| `POST /providers/:id/rotate` | إصدار جديد وتبديل آمن بضبط تعارض وidempotency؛ لا تفعيل تلقائي. |
| `POST /providers/:id/disable` | تعطيل وإبطال cache وسجل إعدادات؛ منفصل عن الحذف. |
| `POST /providers/:id/activate` | يتطلب موافقة نشر/تفعيل منفصلة وأهلية قائمة؛ غير جائز لـGemini في الإنتاج. |
| `GET /audit` | بيانات تدقيق مصفاة لمخوّل فقط، لا أسرار أو محتوى طالب. |

لاحقًا: 401 بلا جلسة، 403 عند غياب الصلاحية أو منع الأهلية، 409 للتعارض، 503 عند نقص تبعية أو موافقة صالحة. لا endpoint لقراءة المفتاح أو تصديره. لا زر أو حقل للمستخدمين الطلاب.

## شروط القبول قبل بناء واجهة إدخال

1. إثبات مصادقة المدير وMFA وإبطال الجلسات وتطبيق الصلاحيات وCSRF على الخادم باختبارات HTTP سلبية.
2. اختيار مخزن أسرار حقيقي واختبار أذون هويته، فصل البيئات، النسخ/الاسترداد وعدم تسريب الأسرار في الاستجابات والحزمة والسجلات والتخزين المحلي والعادي.
3. اعتماد مزوّد محدد وفق شروط جمهور نون، وتسجيل موافقة قابلة للانتهاء؛ Gemini مستبعد من الإنتاج، ولا قرار ضمني لربط OpenAI.
4. إثبات إضافة/تدوير/تعطيل وتعارض وفشل جزئي وإبطال cache وتدقيق معتم ومقاومة logging على بيانات اختبار اصطناعية فقط.
5. موافقة مستقلة لربط المزوّد/إضافة السر ثم تفعيل الميزة، مع مراجعة خصوصية وسلامة الطلاب وحدود الاستخدام والتكلفة.
6. حسم مصدر حزمة الإنتاج ومطابقتها للمراجعة وخطة التراجع قبل أي إصدار مستقبلًا. لا تعديل Hostinger ولا نشر من هذا الفرع.

## نتائج التحقق

نجحت `npm test` (بما فيها اختبارات تعطيل AI واختبار الحاجز الجديد)، و`npm run lint`، و`npm run build`؛ السجل الكامل في [`evidence/validation.log.txt`](evidence/validation.log.txt). اختبار الحاجز يغطي 42 حالة طريقة/مسار إضافة إلى JSON التالف والكبير، ويؤكد ترتيب تركيبه في ملف الخادم قبل محلل الطلبات والـSPA. يحوي سجل الاختبارات القديم تسميات Gemini لا تعني مكالمات فعلية أو اعتماد المزوّد؛ اختبار التعطيل يمنع الشبكة صراحة. تحذيرات البناء تخص `__dirname` وحجم الحزمة، وليست فشلًا.

مراجعة مستقلة قرأت الأساس وأكدت غياب المصادقة/المخزن/التدقيق؛ رصدت تركيب الحاجز قبل اكتمال تحرير الخادم. عولج هذا الربط واختُبر لاحقًا في هذا الفرع. لا تدعي هذه الاختبارات اكتمال منظومة إدارة مفاتيح أو تدقيق بنية الإنتاج، ولم نشغّل اختبارات متصفح جديدة أو اتصال مزوّد. الفرع محلي فقط؛ لم ندفعه إلى GitHub لتجنب تشغيل أي نشر آلي غير محسوم، ولم ننشئ PR أو نغير main.
